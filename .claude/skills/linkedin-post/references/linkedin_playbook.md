# LinkedIn 演算法與排版 Playbook

針對技術 / B2B 內容在 LinkedIn 的觸及策略。不是 FB、不是 Threads。

## 演算法基本面（2026 現況）

LinkedIn 在貼文發出後 1 小時內衡量：

1. **Dwell time（停留時間）** — 最強信號。比讚還重要。
2. **留言（特別是 > 5 字的留言）** — 觸發二次擴散到留言者的網絡
3. **儲存** — 次強信號（高品質內容指標）
4. **重新分享** — 強，但 LinkedIn 重新分享率本來就低
5. **讚** — 最弱信號

**對應策略**：
- 寫得讓人想讀完 → dwell time 高 → 觸及高
- 結尾問題要能引出 > 5 字的真實回應，不是「+1」「同意」
- 提供「值得收藏」的清單 / framework → 引導儲存
- 不要追求讚數，那是落後指標

## 長度策略

| 用途 | 繁中字數 | 為什麼 |
|---|---|---|
| 一般技術 insight | 700-1100 | sweet spot，停留時間夠又不會被滑走 |
| 深度反思 / 教學 | 1100-1500 | 上限，超過要拆 |
| Hook 測試 / 觀念短文 | 300-600 | 適合單一強觀點 |
| 拆篇（part1/part2） | 每篇 700-900 | part1 結尾埋鉤、part2 開頭接得上 |

英文夾雜（專有名詞）算字數時當 1 字。

## 排版規則

```
[Hook 第 1 行]
[Hook 第 2 行 — 轉折]
                              ← 空行（重要！讓 hook 視覺獨立）
[第 1 段：場景 / 痛點，1-2 句]

[第 2 段：核心 insight 或工具引入，2-3 句]

[第 3 段：我的具體經驗 / 數據，2-3 句]

[第 4 段：延伸 / 對讀者的意義，1-2 句]

[結尾：開放式問題（留言誘因），1 句]

[hashtag 3-5 個，同一行]

🤖 本文為 AI 產生的貼文
```

要點：
- 每段 ≤ 3 句
- 段間必空行（LinkedIn 是空行讀者）
- 列點用 `→` 或 `•`，不用「1. 2. 3.」（除非真的有順序）
- 全形標點符號（繁中專案一致）

## Hashtag 策略（受眾鎖台灣）

- **數量**：3-5 個。多了像 SEO 垃圾，少了流量池進不去
- **位置**：全部放最末段一行內，不要散在文中
- **混搭**：1-2 個通用大池 tag（如 `#AI` `#SoftwareEngineering`，演算法分類用）+ 2-3 個台灣科技圈常見 tag（如 `#台灣工程師` `#軟體工程師` `#職涯`，視內容挑）
- **不要**為了國際觸及全用英文 tag — 受眾是台灣讀者與台灣公司，觸及到國外受眾是浪費流量池配額；中文 tag 才會進台灣同溫層的 feed

## 連結策略（重要）

LinkedIn 演算法對含外部連結的貼文降觸及 30-50%。對應策略：

- **正文絕不放主連結**。改成「連結放留言」或文末「來源見留言」
- **GitHub / 工具 demo 連結** → 放第一則留言（作者本人發）
- **若一定要在正文出現**：放在最後一段且非超連結形式（純文字 URL），減少演算法懲罰
- 本專案目前的 baseline post（如 post-31）正文嵌入 YouTube 連結 → 改寫時應移到留言區或加註

## 結構變化（避免模板感）

「排版規則」的模板是 baseline，不是每篇照抄的鐵律。讀者連看 3 篇結構一模一樣的貼文，就會聞到 AI 味 — 模板重複本身就是 AI 痕跡。連續貼文要刻意錯開：

- **Hook 公式輪替**：上一篇用 H1，這篇換別的（動筆前掃最近 3 篇 posts 的開頭）
- **收尾輪替**：留言誘因 ≠ 一定要問句收尾。輪著用 — 開放式問題 / 一句有立場的判斷（邀讀者反駁）/ 給讀者的下一步動作（「今天就去檢查你的 X」）
- **段數浮動**：4-6 段之間變化，別每篇都剛好 5 段
- **emoji 用法變化**：有的篇完全不用，別讓每篇都長出同位置的 emoji

不變的是功能：每篇都要有 hook、有一個 insight、有第一人稱經驗、有讓人想留言的理由。變的是形式。

## 留言誘因設計

**爛**：「你覺得呢？」「歡迎留言討論」「有什麼想法嗎？」

**好**：
- 「你最近一次砍掉自己寫的程式碼是什麼時候？為什麼？」
- 「如果讓你只留下一個 AI 工具，你會留哪個？」
- 「你的團隊目前用 Markdown 還是 HTML 給 PM 看 AI 報告？」

**設計原則**：
1. 與讀者個人經驗有關（不是抽象觀點）
2. 答案能在 3 秒內想到（門檻低）
3. 答案需要 > 5 字才能講清楚（高權重留言）
4. 沒有標準答案（鼓勵不同立場留言互動）

## 診斷現有貼文（G3）

讀目標 post 後，依此打分：

| 維度 | 通過標準 | 常見失敗 |
|---|---|---|
| Hook | 前 2 行能獨立勾住點擊 | 在鋪背景、太抽象 |
| Insight 聚焦 | 全篇講 1 件事 | 把 issue 所有論點全塞 |
| 第一人稱 | 至少 1 段「我」做主語的經驗 | 全篇第三方觀察 |
| 排版 | 段 ≤ 3 句、段間空行 | 大段落、無空行 |
| 留言誘因 | 開放式、與讀者有關 | 自我總結式收尾 |
| 連結 | 不在正文 | 嵌在正文中段 |
| Stop-slop | 全項通過 `config/stop-slop-guidelines.md` | 「綜上所述」、被動語態 |

各維度 1 行說明「目前狀況 vs 建議改法」，讓使用者決定要不要動。

## 同主題不同 angle 範例

同一個 issue（如「AI 產 200 行 Markdown 報告很難讀」），不同 angle：

- **H1 自白角度**：「我以為換成 HTML 報告會解決問題。沒想到根本不是格式的事。」
- **H3 場景角度**：「上週我審一份 AI 寫的 250 行 Markdown 投資日報。讀完花了 14 分鐘。」
- **H6 數字角度**：「200 行 Markdown 報告，AI 寫 8 秒，我審 14 分鐘。瓶頸不在 AI。」
- **H2 反主流**：「AI 工程師都在加速生成。但效率瓶頸早就跑到下游。」

挑一個寫一篇，不要混。
